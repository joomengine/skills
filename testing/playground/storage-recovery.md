# Recover a Playground storage failure without losing the build

Use this when Playground reports `QuotaExceededError`, `Playground Storage Quota limit reached`, an IndexedDB write failure or a failed persistence indicator. Keep building through JCB after recovery; these errors do not justify hand-coding the component elsewhere or treating JCB as unable to build large systems.

## Identify what failed

**Browser storage is not browser memory or PHP memory.** IndexedDB quota, available disk, browser/profile restrictions, closed connections and failed storage transactions need their own diagnosis. The displayed message alone neither proves the physical quota was exhausted nor proves the agent did something wrong. Repeated old sites, retained backups or legacy deployment images can consume storage; inspect actual inventory and the browser's usage/quota estimate rather than assume a cause. Clearing HTTP cache alone does not reliably clear IndexedDB.

Record the exact error, action, time, browser/profile, site key, deployed Playground `assets/manifest.json` `sourceCommit`, installed Joomla/JCB/PHP versions and storage estimate if available. Determine whether the Joomla operation completed and only its subsequent persistence failed. Check the saved record or response before retrying: replaying a successful import, payment or other mutation can duplicate its effect.

**Version gate:** merged [PR #24](https://github.com/joomengine/playground/pull/24), commit `c403f035`, separates completed requests from persistence failures and keeps complete live export available. Its Rocket interface always persists and ignores `persist=0`. The live manifest still reported `c49d025` on 2026-11-14 during this source review; verify the deployed build rather than equating merged with deployed. [Evidence and implementation map](sources.md#workspace-lifecycle-refresh-2026-11-14).

## Preserve, download, restore, verify

1. **Keep the original owner tab and live runtime open.** Do not reload, Stop, Reset, delete the site, clear its storage or close it while this may be the only current copy. Avoid starting a replacement deployment in that workspace. Preserve intended unsaved editor buffers separately; a full export cannot capture an unsubmitted Joomla form or an unsaved editor draft.
2. **Download → Complete site from the live site**, even when persistence failed. A successful Playground Save or browser-held backup is not a prerequisite. On post-PR #24 builds, if **Back up current site** or **Update this backup** fails, download the already-prepared archive offered by the error instead. The previous stored backup remains unchanged, so it does not contain the latest changes merely because it still exists.
3. **Verify the external artifact.** Confirm the actual ZIP arrived outside origin storage, record byte size and SHA-256, and inspect the required `site/`, `database.sql`, `database.ndjson` and `export.json` structure. Preserve its layout and private account/application data. A Share link, recipe JSON, compiler installer, browser-held backup or files-only ZIP is not this complete recovery package. Follow [complete-site delivery](../../workflows/delivery.md#preserve-and-restore-a-complete-playground-site).
4. **Restore into a genuinely clean browser storage context** using Playground **Upload**, with compatible supported versions. A separate browser profile/context provides isolation without deleting the original; an ordinary new tab on the same origin does not. In newer builds, companion windows share the owner runtime. Confirm the destination is empty or its own work is already backed up before Upload replaces it. Do not clear an occupied profile just to make the test look clean.
5. **Verify restored state, not only a success toast.** Check login, actual installed versions, component and view/Field records, definitions and identities, parent/child relationships, representative database rows and the latest files. Reopen and save a controlled record; reload and verify it. Compile, install and exercise a representative consumer from those restored JCB definitions before declaring the build recovered. Record any stage not run and keep the original until recovery is accepted.
6. **Only then clean up the chosen old data**, within the user's authorized scope. Prefer the post-PR #24 **Backups** storage manager: inspect old live stores, legacy images, backups, recipes and preferences, and retain required backups. It protects active/locked stores and does not clear unrelated origin data; unassigned stores need individual confirmation. Do not delete all browser data or other projects. If using origin-level cleanup, first preserve every affected site and retain the verified full download outside that origin.
7. Continue from the restored JCB workspace, retaining the full archive and receipt until the user's delivery is secure. If storage failures recur, record measured usage, failing operation and deployed revision for [Skills feedback](../reporting-issues.md); avoid unbounded retries or accumulating replacement sites/backups.

## When full export or restoration is blocked

Keep the original live owner open and report the precise failing stage. If Joomla cannot boot, **Recover saved site** may provide stored recovery data. If MariaDB cannot start, its files-only recovery has no SQL database: label it partial, retain all available artifacts and do not reset the source. A storage estimate or a `512 MiB` checkpoint message does not by itself prove the archive is oversized; inspect the original export/error before assigning that diagnosis.

On older builds, [issue #11](https://github.com/joomengine/skills/issues/11) reported that an independent `fresh=1&persist=0&start=0` session could render forms, while switching the failing owner in place caused `IDBDatabase connection is closing`. That is historical environment diagnosis, not proof of a recovered build or clean storage. It does not transfer the unsaved source and must not replace the complete download/restore procedure. Do not carry this temporary-mode URL forward as a current Rocket workaround.

## Acceptance and evidence boundary

The upstream `site-backups.browser.mjs` test injects continuous persistence failures, verifies the completed mutation ran once, exports/downloads the latest live site while failures continue, and restores it in a clean context with matching records, relationships, files and credentials. It also tests failed backup replacement retaining the prior archive. This is a useful test contract and upstream evidence, **not a new manual recovery run performed for these Skills changes**. It does not prove atomicity across live PHP and database stores or explain every real quota failure. Record the user's actual source state, artifact and restored runtime separately.
