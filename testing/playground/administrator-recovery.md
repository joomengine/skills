# Recover administrator access in Playground

Use this after **Upload** or when reopening an owned, authorized sandbox whose Joomla administrator does not open. Treat storage, site startup and authentication as separate checks. If the upload did not become the active, saved site, follow [storage recovery](storage-recovery.md) first. Do not change accounts on another preview, a shared test deployment or a production site.

## Sign in to the restored site

1. Verify the active site is the intended restored workspace. If its Joomla administrator is already open and authenticated, continue there. If not, open **Admin**, or use **Login details → Open administrator**, and wait for the actual Joomla login form in the preview.
2. Open **Login details → Login**. It submits the native Joomla form already displayed; it does not navigate to it, change the password or prove authentication. **Sign in automatically** is a launch/session setting, not a password recovery option. Verify the administrator opens and the expected JCB project is present. If the preview is on the wrong page, navigate to the administrator first instead of repeating the button.
3. If **Login** is disabled or the saved password is rejected, use known current credentials privately in Joomla. Alternatively, inspect only the root `export.json` of the exact private **Complete site** ZIP. At the inspected revision, `playground.configuration.admin` contains `username`, `email`, `name` and the saved sandbox `password` when the export includes Playground configuration. Make one attempt with a plausible archived credential on the restored site's own Joomla login form. If Joomla rejects it, do not keep trying it. If Joomla demands an additional normal authentication step, follow that step rather than altering account protections.

**What the archive proves:** the password in this metadata is the last one Playground saved, not necessarily the current Joomla password. Upload checks an embedded saved credential against the restored account. Stale credentials can leave the restored site running with **Show** and **Login** disabled; the account is not overwritten just because the metadata is stale. A compatible older export without a saved password can take a different restore path; verify its actual account instead of assuming the same behavior. Browser sessions are not part of the ZIP. The inspected **Login details** fields are read-only; typing into the Joomla form does not write credentials back to Playground metadata.

Keep these ZIPs private: they can contain **plaintext sandbox credentials** and other application data or secrets. Never put credentials or raw metadata in chat, tool logs, screenshots, Git, public links or verification receipts. Use protected entry/storage and report only whether the expected credentials were present and accepted.

## Recover on a copy, then verify the next export

If a current password or another authorized Super User is available, prefer normal Joomla administration to regain access. Check the export separately: updating the account in Joomla does not by itself update Playground's saved login. For a self-contained Playground handoff, use the built-in copy/administrator operation where supported:

1. Keep the original Complete site ZIP and the uploaded source intact. On the **uploaded** site, open **Configure deployment**, give the copy a distinct name, and set its **Administrator** details deliberately, using a new private sandbox password. Keep the installed Joomla/JCB selection and unrelated settings unchanged. Use **Use this deployment** for an independent copy with the uploaded site's data; do not use **Apply to this site** as a password reset. First confirm the target is an uploaded site: that same command on an ordinary recipe can instead start a clean installation.
2. Confirm the copy has a new site identity, preserved JCB records/files and working administrator login. This feature can replace the first active Super User on the **copy**, including identity details; it is not a selector for an arbitrary account. Reserve it for an authorized disposable sandbox where that account is the intended one. If the installed build lacks the feature, the copy fails, or account ownership is ambiguous, keep the backup and use an authorized Joomla administrator or supported Joomla recovery route. Do not improvise a database update, create a privileged user, or change account protection settings to make login succeed.
3. From the recovered copy, **Download → Complete site** and retain the replacement archive privately. Inspect that the saved administrator in its metadata matches the intended credentials without exposing the values. Upload the **exact new ZIP** into a clean storage context and verify the Joomla administrator login and representative JCB state again. Until that passes, distinguish **access regained** from **new archive verified**. Keep the prior archive until the new one is accepted.
