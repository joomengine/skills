## Canonical agent guide consolidation: 2026-11-09

The [Skills Playground guide](README.md) is the canonical agent workflow for using Playground to build and deliver extensions. Playground's footer and repository README link directly to it; `docs/agent-guide.md` in Playground retains a short forwarding notice for existing links. Playground implementation and contributor documentation stay in the Playground repository. Historical guide links in this ledger identify the material inspected at the time, rather than a second maintained operational guide.

Compared the proposed [agent guide at `d137949`](https://github.com/joomengine/playground/blob/d1379494a682ed3507a858e6e160b151b61e5fe4/docs/agent-guide.md) with the existing Skills workflow and Playground implementation at [`df82e34`](https://github.com/joomengine/playground/commit/df82e34a104019c34bcbfd251d37bd9d88d347a0). Operational coverage is maintained as follows:

| Guide content | Canonical destination |
| --- | --- |
| Request, browser operation, JCB source models, repositories, Init/Pull/Reset/Push, compilation and debugging | [Playground guide](README.md), with the linked architecture/model and authoring workflows |
| Setup controls, version selection, extension packages, recipes, saved sites, images and recovery | [Configuration and lifecycle](configuration.md) |
| Installers, complete-site export, independent Upload, dependencies and native hosting | [Delivery workflow](../../workflows/delivery.md) |
| Reproducible skill gaps and maintainer feedback | [Issue reporting](../reporting-issues.md) |

Catalogue implementation is documented by [build discovery and staging](https://github.com/joomengine/playground/blob/df82e34a104019c34bcbfd251d37bd9d88d347a0/scripts/version-catalog.mjs), the [browser catalogue reader](https://github.com/joomengine/playground/blob/df82e34a104019c34bcbfd251d37bd9d88d347a0/src/version-catalog.mjs), [configuration](https://github.com/joomengine/playground/blob/df82e34a104019c34bcbfd251d37bd9d88d347a0/src/config.mjs) and the [Pages workflow](https://github.com/joomengine/playground/blob/df82e34a104019c34bcbfd251d37bd9d88d347a0/.github/workflows/pages.yml). The inspected build discovers stable/nightly/upcoming releases, stages full packages, verifies published SHA-256/SHA-512 values and records a SHA-256 content fingerprint where no full-package checksum is supplied. The published catalogue records `generatedAt`. The inspected publishing schedule is 03:15 UTC daily and on `main` changes, with validation before publication; a failed build leaves the prior deployment intact. Selector refresh reads this published catalogue and does not upgrade a saved installation.

Use the [version policy](../../standards/version-policy.md) to choose releases at task time. Commit URLs, package hashes and versions in this ledger identify evidence and historical results; they do not require future builds to use those revisions.

## Freshness and maintenance

1. Record the date and current Playground branch SHA through its authoritative repository. Compare the changed paths with this ledger; do not update the date alone.
2. Inspect the live `assets/manifest.json` where accessible and record its `sourceCommit`, runtime catalogue and package/provenance references. If tool capabilities prevent inspection, say so and record observable versions; do not assume live equals `main`.
3. Inspect the actual running JCB installation/version, especially for a reused saved site. Compare relevant importer/controller/compiler source to the module's separate JCB baseline; investigate differences before applying old assumptions.
4. Recheck `versions.json`, deployment catalogue/recipes, configuration parser, derived-package overlays and affected lifecycle/API files. Version labels, URL support, browser requirements and MCP capabilities may change independently.
5. Run the affected candidate acceptance stages in a fresh suitable site. Record identity/source resolution, package provenance and actual results. Keep historical receipts dated; a newly passing scenario does not retroactively expand an older result.
6. Update configuration links, common instructions, source map and affected module links together. Advertise new Joomla/PHP/prerelease targets only when the published catalogue, compatible recipe and relevant execution evidence support them. Record remaining native/browser/provider gaps explicitly.
