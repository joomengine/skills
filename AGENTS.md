# Agent operating contract

This is the official **JoomEngine Skills** repository for the **whole Joomla Component Builder (JCB) ecosystem**. Joomla Packaging Engine Skills covers the complete journey from an application request through reusable entities, custom PHP behaviour, compilation, installed validation and delivery. Follow the task's relevant skill, module and verification status; do not impose one entity's file format, dependency rules, or identity semantics on another.

## Start here

1. Read `SKILL.md` for task routing and `README.md` for module status. Use `registries/skills.json` to locate the selected model's concise skill entry point. Keep the complete distribution together as described in `standards/skill-loading.md`.
2. Read the selected module's entry point, contract, and relevant workflow. Load supporting references only as the task requires.
3. Before changing implementation-dependent behaviour, inspect the authoritative source at the target revision. The core [Joomla Component Builder repository](https://github.com/joomengine/Joomla-Component-Builder) is the final authority for JCB implementation and compiler behaviour; use the relevant model repositories for their authored definitions. Documentation records verified behaviour; it cannot override a changed implementation.
4. Before extending these docs, follow `standards/module-authoring.md`. Use the same module contract, evidence discipline, workflows, validation, and completion criteria for every future subject.
5. For implementation work, follow the module's `test_workflow` in `registries/modules.json` and the shared [Playground integration workflow](testing/playground/README.md). Testing must exercise the affected model, its real consumer and the intended Joomla/PHP target.

## Non-negotiable project policy

- Deliver a complete, stable, runnable extension ready for deployment on the agreed target, following the [completion contract](workflows/delivery.md#completion-contract). Carry the task through the requested final artifacts; use real build experience to improve the skills through the [Skills issue feedback loop](testing/reporting-issues.md).
- Use the latest JCB for new builds under the [version policy](standards/version-policy.md). Resolve the current production release at execution time; use alpha/beta channels for the corresponding development task. Pinned source citations are historical evidence, not a requirement to install that old build.
- Maintain the guide for using Playground to build extensions in [Skills](testing/playground/README.md). Playground's runtime Agent link leads there. Keep documentation for developing Playground itself in its own repository, with references rather than duplicate agent guides.
- Start new builds with JCB definitions. Do not hand-code a new component/scaffold/schema and then Extrude it back into JCB; reserve Extrusion for genuinely pre-existing migration inputs. Native definition-repository and authorized MCP authoring remain valid routes, with JCB import/compilation and Playground validation.
- Keep implementation within JCB's native authoring and compilation architecture. Do not add independently maintained application code, plugins, modules or override packages that bypass it without explicit user authorization. Recommend the native path for reproducible compilation, reuse and maintainable delivery; follow the [authoring boundary](standards/authored-code.md#keep-implementation-inside-jcb), which permits JCB-authored Powers, plugins/modules and supported assets without routine approval pauses. Use the [request-to-extension workflow](workflows/request-to-extension.md) for application requests. The earlier repository-only authoring MCP scope does not limit these community skills.
- JCB intentionally gives advanced authors architectural freedom. Let its existing features do the routine work: acquire complete reusable implementations from the [reference patterns](examples/reference-patterns.md), use [Dynamic Get](packages/workflows/dynamic-get.md) for ordinary page retrieval, and compose Templates and Layouts. Add custom services for a concrete unmet need, not merely to wrap generated behaviour.
- Prefer immutable application GUIDs for new cross-table relationships and portable data exchange while retaining Joomla numeric primary keys. Keep definition GUIDs, row GUIDs and business keys distinct. Follow [application identities](packages/workflows/application-identities.md), including deliberate ID alternatives and migration boundaries.
- For subforms persisted to separate tables, author and attach an actual Admin View for every persisted child entity, with its schema, identity and access policy. Use the [normalized subform workflow](packages/workflows/normalized-subforms.md) for get/save handlers, dependency closure and failure semantics; XML alone is not separate-table persistence.
- Reuse the complete [Files/File Types feature](packages/workflows/media-files.md) when managed uploads or image cropping are required. Model managed categories and similar vocabularies as linked entities through [modal relationships](packages/workflows/modal-relationships.md); text inputs do not supply those features.
- Build custom algorithms and integrations in cohesive Super Power PHP classes, with actual callers and service construction. Use Joomla Powers for version-appropriate Joomla class references. Verify namespace-driven administrator/site/library placement and loaders using the [PHP customization workflow](super-powers/workflows/customize-extension.md); do not mistake a JPK reference for a custom class implementation.
- Search for reusable Fields, views, queries, layouts and supporting models as well as classes. Use the [entity reuse procedure](standards/entity-reuse.md): unchanged reuse retains identity; an independent adaptation gets its model-appropriate new identity and coherent reference remapping. Intentional same-identity overrides remain a separately declared maintenance choice.
- Never access or probe `git.vdm.dev` from an agent, including offline-node recovery, redirects and configured Git rewrites. Prefer advertised eligible Codefloe and Codeberg mirrors as described in the shared network procedure. Human issue-reporting links are for the human to open.
- Investigate supported **Joomla core/framework** capabilities first; then `joomengine/super-powers`, the central shared foundation and reference standard; then specialist Power repositories. Reuse suitable code through composition, dependency injection, or inheritance before creating a new implementation.
- In a Super Power repository, `settings.json` and `code.power` are authoritative import inputs. Keep generated `code.php`, indexes, and documentation consistent; a PHP-only patch does not update the imported power.
- For Super Powers, preserve existing GUIDs. Generate new UUIDv4 identifiers with a cryptographically secure system facility and check all registered current indexes plus task-specific repositories before use. Other JCB entities must follow their own module's identity contract; some use natural keys instead of GUIDs. Preserve repository order and provenance when resolving dependencies.
- For Field Types, `joomengine/joomla-fieldtypes` is the official core catalogue; for Snippets, `joomengine/snippets` is the official core catalogue. Every repository in the corresponding domain must include its current core catalogue in new-identity collision checks, together with additional configured repositories and local additions. A distinct new item receives a fresh GUID. An improvement or intentional fork override of the same existing item retains its GUID and records the intended resolution order. Never assign a core identity to an unrelated item.
- For Packages, select the exact model contract before changing identity or serialization. Standalone GUIDs, parent-keyed children, natural keys and file/folder pointers have different rules. Preserve the full affected graph, source provenance and external Field Type/Power dependencies. Inspect every eligible writable package repository before Push; the inspected exporter does not provide a single-destination selection guarantee.
- Use the [shared repository network workflow](standards/repository-network.md) to discover maintained public core mirrors and reduce GitHub reads. Prefer monitored status-1 endpoints; a status-0 endpoint may receive a bounded recovery probe. Discover new targets dynamically, preserve canonical identity/order and actual transport/revision provenance, and keep contribution destinations separate.
- Preserve portable placeholders, field-specific empty/null/sentinel values, public contracts, and upstream licensing. Follow the repository's tabs and established code style.
- Follow the [authored-code standard](standards/authored-code.md) for readable PHP, JPK/SPK references, focused hooks and presentation composition. When placement is unclear, use the compiler's temporary tracing toggles and a comment probe under [GUI tracing](packages/workflows/debug.md#trace-a-gui-code-field), then correct the authoring source and regenerate.
- Distinguish **project policy**, **verified implementation behaviour**, **observed examples**, and **unverified gaps**. Cite exact source revisions for implementation claims. Never present an inferred or untested feature as verified.
- A successful static check does not prove a JCB import, compilation, or runtime integration. State which checks actually ran and which remain unavailable.
- When browser access and a suitable supported target are available, use Playground by default for authorized implementation validation, unless the user opts out or the task does not affect executable behaviour. Choose the requested versions, verify the installed JCB version, import or refresh the candidate, inspect persisted values, and compile and exercise a real consumer where relevant. Record blockers and unrun stages honestly; browser availability alone is not a pass. Do not add a routine permission pause to already authorized testing. Ask when missing scope, private data, credentials, publication or external effects require the user's decision.
- Use JoomEngine Code to inspect or diagnose generated/installed output. Carry lasting fixes back to the authoritative repository definition, blueprint or compiler source and regenerate; an editor-only patch does not prove the maintained source works.
- Report failed outcomes and guidance gaps to `joomengine/skills` through the [feedback workflow](testing/reporting-issues.md). This is separate from upstream JCB issue submission, which remains human-led: prepare a minimal, sanitized reproduction for the [official JCB issue chooser](https://git.vdm.dev/joomla/Component-Builder/issues/new/choose).
- Stay within the requested scope and authorization. Make work reviewable through focused commits and a PR when requested; do not merge merely because checks pass.

## Documentation quality

Write exact operational instructions: inputs, source authority, ordered actions, outputs, checks, and failure recovery. Explain consequential edge cases. Avoid repetitive essays, invented defaults, empty templates, hidden assumptions, and aspirational features described as implemented. Keep one canonical explanation per rule and link to it.

Root documentation remains ecosystem-wide. New modules must be discoverable from the root and the module registry, and must declare their scope, version applicability, evidence, limitations, and completion status.
