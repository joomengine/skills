# Verify an application import and export contract

Use this checklist with the [immediate](immediate-import.md) or [staged](staged-import.md) workflow. Start from JCB's native uploader, mapping, spreadsheet services, generated models and reusable Powers. The tests below help select and verify their configuration; they do not require a replacement importer, a particular business key or a new persistence framework.

**Authority:** acceptance guidance derived from the core source observations below. Inspected **11 November 2026**, core JCB `6.x@037752c7e6599aa4cec900138dfb61af7ee4ba8f`. These are source findings, not new runtime results. Use the [latest-version policy](../../standards/version-policy.md) and inspect the actual compiled consumer and installed dependency versions before applying them.

## Choose the failure promise before testing

Keep these outcomes distinct in the interface, implementation and test report:

| Promise | Required evidence |
| --- | --- |
| Row-by-row import | Valid rows persist and invalid rows are reported, including when a later row fails. Reconcile displayed totals with saved data. |
| Whole-file pre-validation | All selected rows, mappings and required references are checked before the first application write. An invalid final row leaves earlier valid rows unapplied. This demonstrates **pre-write rejection**, not transaction rollback. |
| Atomic write batch | After valid input passes, deliberately fail a later write and prove earlier writes in the declared boundary are rolled back. Include parent, child, relationship and asset writers that participate; disclose effects outside that boundary. |
| Stale-update protection | Change the target after preview, then attempt execution. The required lock or revision check is enforced at the actual write boundary. Pre-validation and transactions alone do not define this policy. |

Pre-validation can be the complete solution when the requirement is “reject invalid input before applying it.” Do not introduce a transaction layer for that requirement alone. Conversely, valid input can still encounter a storage failure or concurrent change, so do not describe pre-validation as protection against every partial write. When atomicity is required, follow [save boundaries](normalized-subforms.md#place-the-transaction-correctly) and test the exact Joomla/database lifecycle.

Use the same file, sheet, mapping and value normalization for validation and execution. Bind any stored preview to its authorized operation and invalidate it after those inputs change. Inspect validation dependencies for side effects: core [Import Item::getImportValue/setLocalValue](https://github.com/joomengine/Joomla-Component-Builder/blob/037752c7e6599aa4cec900138dfb61af7ee4ba8f/libraries/vendor_jcb/VDM.Joomla/src/Componentbuilder/Import/Item.php) can create missing linked records while resolving values. Calling the ordinary row processor in a “preview” is therefore not proof of a write-free validation pass. Reuse suitable read/validation services without invoking creation until the write phase.

The inspected [Transient::execute/import](https://github.com/joomengine/Joomla-Component-Builder/blob/037752c7e6599aa4cec900138dfb61af7ee4ba8f/libraries/vendor_jcb/VDM.Joomla/src/Componentbuilder/Import/Item/Transient.php) processes and writes rows as it iterates, catches row failures and can continue. The application may compose its native extension points to provide another policy; test the policy actually authored rather than assigning it to every JCB importer.

## Exercise the spreadsheet values users will supply

Choose fixtures for every advertised format. Compare the original logical values with **preview/mapping, validation, persisted records and any exported round trip**, not only the success banner. Reuse the installed spreadsheet reader instead of splitting CSV on commas or line breaks.

| Fixture | Assertion |
| --- | --- |
| CSV field with a comma, doubled quote and embedded newline | Each remains one field in one logical record; later columns and row diagnostics remain aligned. Include CRLF/LF input where supported. |
| Non-ASCII text; UTF-8 with and without a BOM | Text survives unchanged and the first header has no invisible BOM prefix. State any other accepted encoding and its conversion/rejection policy; do not claim every encoding is supported from an extension check. |
| Text identifier `00123` and numeric zero `0` in separate columns | The identifier retains its leading zeros; zero survives required-value checks and saving when valid for that field. Distinguish omitted, blank, null and zero. A zero business key needs its own matching test, not just a zero quantity test. |
| Workbook text cell `00123` versus numeric `123` displayed with a `00000` format | Establish whether the contract uses stored or formatted values. A reader cannot recover an original text identifier from a number merely because the screen displays padding. Keep identifier columns as text in a suitable example file. |
| Extra unmapped column between required columns; reordered columns | Mapping follows the chosen columns rather than position assumptions. Extra columns are ignored or rejected according to the advertised policy; never silently mapped to an unrelated writable field. |
| Duplicate/empty headers, duplicate target mappings, missing required target | The mapping UI and server agree on acceptance; ambiguous or unauthorized mappings do not reach a write. Identify the relevant source column in the error. |
| Two-sheet workbook with distinct headers/rows and the second sheet active | Preview and execution use the same declared sheet. First-sheet-only is a valid application contract; it is not a universal JCB requirement. Test the unselected sheet is not accidentally applied. |
| Blank rows, trailing cells, empty/header-only file and expected maximum volume | No silent prefix import or row/column loss. Report skipped/rejected rows under the chosen policy and fail visibly on an actual resource limit. |
| Formula cell, if workbook formats are advertised | Define literal versus calculated-value handling and test it. Treat untrusted text as data on export; a round trip must not unexpectedly turn an identifier or text value into a formula. |

**Source points to inspect:** [Header::get](https://github.com/joomengine/Joomla-Component-Builder/blob/037752c7e6599aa4cec900138dfb61af7ee4ba8f/libraries/vendor_jcb/VDM.Joomla/src/Spreadsheet/Header.php) reads the workbook's active sheet, while [Reader::read](https://github.com/joomengine/Joomla-Component-Builder/blob/037752c7e6599aa4cec900138dfb61af7ee4ba8f/libraries/vendor_jcb/VDM.Joomla/src/Import/Spreadsheet/Reader.php) defaults to sheet index `0`. [FileReader::read](https://github.com/joomengine/Joomla-Component-Builder/blob/037752c7e6599aa4cec900138dfb61af7ee4ba8f/libraries/vendor_jcb/VDM.Joomla/src/Import/Spreadsheet/FileReader.php) uses PhpSpreadsheet identification/readers and `setReadDataOnly(true)`, initially loads the workbook to find its highest row, then reads chunks. Chunked iteration alone does not prove bounded peak memory. [RowDataArray::process](https://github.com/joomengine/Joomla-Component-Builder/blob/037752c7e6599aa4cec900138dfb61af7ee4ba8f/libraries/vendor_jcb/VDM.Joomla/src/Componentbuilder/Spreadsheet/RowDataArray.php) casts `getValue()` to strings. [ParentTable::validateParent](https://github.com/joomengine/Joomla-Component-Builder/blob/037752c7e6599aa4cec900138dfb61af7ee4ba8f/libraries/vendor_jcb/VDM.Joomla/src/Import/ParentTable.php) uses `empty()` for the match field, which rejects `'0'` there. These specific paths explain why exact values, sheets and roles need testing; they do not establish the results of every installed library/configuration.

## Verify the real exporter and the downloaded artifact

1. Trace the visible action through its controller, Factory/provider and resolved exporter class in the installed component. Read the actual `export()` signature, argument order/names, supported writer selection and output behavior. Compare the maintained Power definition with the generated class when adaptations exist.
2. Keep example headers and mapping targets in the same maintained definition, as required by the [complete-feature contract](imports.md#deliver-a-complete-import-feature). Check the output format is accepted by the uploader and reader. Do not infer an `Xlsx` writer from an `.xlsx` label or filename.
3. Click the real action and retain the resulting file. Check filename/extension, response content where observable, nonempty bytes, actual format, worksheet/header order and representative cell values with a compatible reader. A button click, HTTP success, redirect or “exported” message does not demonstrate a download. A manually constructed input file cannot substitute for this check.
4. Fill the downloaded example with a synthetic row, upload it and complete mapping/execution. For an export of existing data, compare identity/text/zero values and requested columns before and after the supported round trip. A single empty example proves neither populated exports nor lossless updates.

**Verified source contract:** [Spreadsheet service provider](https://github.com/joomengine/Joomla-Component-Builder/blob/037752c7e6599aa4cec900138dfb61af7ee4ba8f/libraries/vendor_jcb/VDM.Joomla/src/Componentbuilder/Service/Spreadsheet.php) resolves `Spreadsheet.Exporter` to [Componentbuilder Spreadsheet Exporter](https://github.com/joomengine/Joomla-Component-Builder/blob/037752c7e6599aa4cec900138dfb61af7ee4ba8f/libraries/vendor_jcb/VDM.Joomla/src/Componentbuilder/Spreadsheet/Exporter.php). At this revision, `export()` has **no public `fileType` argument**: it initializes `Xls`, switches to `Csv` when the supplied row count exceeds 3000, writes to `php://output` and exits. Its private `fileType` property is not a public setter. It populates cells with `setCellValue()`, so verify identifier/formula typing in actual exports. The [native Example caller](https://github.com/joomengine/Joomla-Component-Builder/blob/037752c7e6599aa4cec900138dfb61af7ee4ba8f/admin/src/Controller/Import_translationsController.php) supplies rows, filename, title and sheet name.

An application-local Power may deliberately add a format option. Preserve that adaptation in its authoritative JCB source and test its dependency/caller contract; do not document its extra parameter as a universal native API or patch installed generated PHP as the lasting fix.

If no file arrives, record exactly that and inspect dispatch, permissions/token, PHP/output errors, headers and browser download handling. Correct the responsible authoring record or Power, regenerate, then repeat the artifact check. Until bytes are obtained and opened, report export as failed or unverified according to the evidence, even if imports pass.

## Preserve fields through the intended native save path

An import that updates a few mapped fields must explicitly define what happens to the rest. Start with the application's existing generated model or reusable Data/Power save path and its validation, permissions, transformations and hooks. Do not bypass it with raw SQL merely to avoid a field-handling problem.

1. Trace the actual writer. Core [ParentTable::processParent](https://github.com/joomengine/Joomla-Component-Builder/blob/037752c7e6599aa4cec900138dfb61af7ee4ba8f/libraries/vendor_jcb/VDM.Joomla/src/Import/ParentTable.php) uses `Data.Item`; its [provider](https://github.com/joomengine/Joomla-Component-Builder/blob/037752c7e6599aa4cec900138dfb61af7ee4ba8f/libraries/vendor_jcb/VDM.Joomla/src/Service/Data.php) composes Data load/insert/update/delete services. That is not automatically the generated administrator model's full `save()` lifecycle. Choose the native path that enforces the application's actual invariants and call its existing validation/authorization as required.
2. Separate an unmapped field, an absent cell, an explicit blank/null and an explicit clear. Pass only intended changes when the selected path supports partial updates. If it expects a complete form payload, load the authorized existing record, preserve needed omitted values in the representation that path expects, and overlay validated mapped changes. Keep immutable identity and protected fields under the model's rules. Avoid blind copying of stored JSON into a path that expects decoded values, or decoding/re-encoding fields unnecessarily.
3. Inspect generated field handling before assuming omission means preservation. For example, core [Language_translationModel::save](https://github.com/joomengine/Joomla-Component-Builder/blob/037752c7e6599aa4cec900138dfb61af7ee4ba8f/admin/src/Model/Language_translationModel.php) has API-PATCH-specific preservation and non-PATCH branches that default omitted collection fields to empty strings. Calling it from an ordinary importer does not automatically activate PATCH semantics. Reuse the supported lifecycle rather than spoofing the HTTP method to change behavior.
4. For a JSON subform, merge selected entries by the declared child/language identity only when the application promises a partial update. For separate-table children, follow [normalized subforms](normalized-subforms.md#understand-replacement-and-failure-behavior): the complete-collection setter can delete omitted children. An omitted collection and an intentionally empty collection must remain distinct. Do not turn a small spreadsheet update into an unintended replace-all.
5. Seed a record with mapped and unmapped scalar fields, a relationship, and at least two subform entries where applicable. Import a change to one mapped value, reopen through the native editor and inspect persisted data. Verify unrelated values, row GUIDs and child identities survive; separately test the advertised explicit-clear operation. Repeat for create and update because their defaults differ.

Core [Import Item::get/processSubform2](https://github.com/joomengine/Joomla-Component-Builder/blob/037752c7e6599aa4cec900138dfb61af7ee4ba8f/libraries/vendor_jcb/VDM.Joomla/src/Componentbuilder/Import/Item.php) builds subform data from mapped columns; it does not load and merge every existing entry. This is a reason to select/test the desired update semantics, not a claim that JCB cannot preserve subforms. Put any required merge or payload preparation in focused maintained hooks/Powers and recompile.

## Name and test each retry behavior

“Retry-safe” is too broad without saying which state is safe. Use the application's stable match key and existing operation/job state as appropriate; a queue or new token store is not required for every importer.

| Situation | Required decision and test |
| --- | --- |
| Validation rejection before writes | Correct input/mapping and validate again. Verify no application rows or linked records were created by the rejected attempt. Define whether the owned upload is retained or replaced. |
| Repeated Apply for the same completed operation | Define whether it is rejected, returns the prior outcome, or safely re-executes under a verified idempotent policy. Check side effects as well as final row values. Test a double submission at the server, not only a disabled button. |
| Fresh upload of the same file | This is a new operation. Verify the matching/upsert policy prevents unintended duplicate records; distinguish stable identity from “no side effects,” since save hooks, timestamps or notifications may run again. |
| Stale preview, token or job | Reject or require a new preview according to the declared validity contract. Test changed mapping/file and expired operation separately; test changed target records when stale-update protection is promised. Expiry is not proof that the first write failed. |
| Timeout, lost response or interrupted worker | Treat the outcome as unknown until saved rows, job/operation state and any relevant side effects are reconciled. Resume/retry only the safe remainder; never blindly rerun because the browser showed no success. |
| Known partial write | Report committed work and failed rows. Retry under the stable matching/side-effect policy or use the declared recovery path; clearing a message or queue status does not undo data. |
| Concurrent requests/workers, if supported | Verify the actual claim/lock or conditional write prevents duplicate effects. Sequential replay success is not a concurrency test. Follow the [staged processing notes](staged-import.md#source-specific-processing-notes). |

For a new Transient attempt, build a fresh payload and capture `execute(...)->result()` once: the inspected implementation removes `payload->maps` and `result()` resets messages. That mutable-object lifecycle is distinct from database idempotency and operation replay protection. Reset/isolate shared services as required by their actual contracts.

## Record bounded completion evidence

Retain target Joomla/JCB/PHP and spreadsheet-library versions, authoring/source revision, synthetic fixture values, actual downloaded artifacts, before/after identities and values, observed errors and cleanup state. Separate **passed, failed, blocked and not run** for downloads, parsing, mapping, create/update, omission/clear, invalid-file rejection, late rollback and each retry/concurrency case. A passing pre-write rejection test must not fill the rollback row; a successful import must not fill the export row. Apply the existing [package verification record](../verification.md) without publishing private input data.
