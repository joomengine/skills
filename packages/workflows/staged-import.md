# Trace the staged Demo importer

Use this path when the application needs upload/mapping now, a retained file and job record, queue/history visibility and processing later. Select it from the [application requirements](imports.md#select-a-reference-from-the-requirements), alongside the [immediate composition](immediate-import.md). ## Acquire and adapt the whole graph

1. Acquire the Custom Admin View's main/custom Dynamic Gets, `importerarea`/`importerqueue` templates, mapping/message/table/modal layouts, uploader Custom Code, queue/file/message Admin Views and Fields, console plugin, Powers/providers and spreadsheet library. Follow [entity reuse](../../standards/entity-reuse.md) for identity and dependency handling. Keep separately stored entities backed by their own attached Admin Views.
2. Reuse the [Files/File Types feature](media-files.md) with the uploader, type/upload/display/delete endpoints and assets. The importer area calls `vdmUploaderConfig` and `addUikitThreeToAdminViews`; preserve that configuration and its dependencies. Configure the import File Type and the file's entity/target link to the queued job. Adapt names and permissions together rather than retaining a Demo table name accidentally. Keep cropping/image behavior only when the requested upload type needs it.
3. Retain the **Example** toolbar action. The specimen's `getImportExample()` calls [`getItemImportFields(true)`](https://github.com/joomengine/packages/blob/4fd6ce1f2a11a478abb291d03a1a3b32ceeda5c9/src/custom_code/getItemImportFields/item.json) and exports its labels through `Spreadsheet.Exporter`; mapping uses the same target-field helper. Adapt the helper's parent/table selection and field policy, then test the actual downloaded file through upload and mapping. Follow the [shared example contract](imports.md#deliver-a-complete-import-feature), not a separate hardcoded sample-header list.
4. Inspect and adapt `saveImportMap()`. The specimen checks CSRF and `importer.access`, records file/mapping plus a job GUID, `import_status=1` and creator, then writes `item_import`. On success it releases the session importer GUID and reports “queued.” Verify the retained file remains accessible to the later processor and is owned by this job; do not delete it with temporary-upload cleanup.
5. Adapt the processing entity and domain services in maintained source. The inspected [ItemImport Power](https://github.com/joomengine/super-powers/blob/9cd980492bed4c8177a6e32b703641950ec93604/src/647316a5-eb42-4bec-82dd-ca0dc2861ad3/code.power) explicitly targets `look`, GUID matching, and `detail` joins using `entity`. These are reference settings, not automatically inferred from whichever component imports it. Align Table metadata, mappings, queue/status/file/message table names and authorization. Reuse suitable Powers; add a focused domain implementation only for behavior the existing services do not provide.
6. Keep queue data in its [Dynamic Get](dynamic-get.md) and render it through the queue template and layouts. Check file names, statuses and row-message modal behavior. Avoid replacing these with a hand-written query and one large controller/view block.
7. Compile the console plugin in the component context, install and enable it, and inspect command discovery. The plugin registers `[[[component]]]:item:import` with Joomla's writable console loader; the command uses `Import.Persistent`, `Data.Items` and `Import.Persistent.Entity`. Confirm the actual expanded command name with the target's command list before invoking it. This plugin has a specific processor-registration role; an immediate importer does not need it merely because the reference has one.
8. Execute the real command against one synthetic queued file. In the verified Playground runtime, **Additional setup steps → startup command** ran `demo:item:import` against the saved site. This is Joomla's native console path; it needs no external importer script or shell subprocess. Follow the [recorded native procedure](../evidence/importer-building-blocks.md#demo-queued-runtime-exercise) and inspect current runtime controls. If unattended scheduling is required, establish and test it separately; a startup invocation is not cron. Inspect application rows, queue state and persisted row messages. Test a subsequent job and retry after an interrupted job; confirm file retention/removal follows the selected lifecycle.

## Source-specific processing notes

The corresponding JCB implementation at `6.x@037752c7e6599aa4cec900138dfb61af7ee4ba8f` was also inspected on 2026-11-09:

- [Console Import::doExecute](https://github.com/joomengine/Joomla-Component-Builder/blob/037752c7e6599aa4cec900138dfb61af7ee4ba8f/libraries/vendor_jcb/VDM.Joomla/src/Componentbuilder/Abstraction/Console/Import.php) reads waiting rows, then updates their status before iterating them. That sequence is not an atomic claim/lease; two workers can read the same waiting jobs. It returns `0` even after counting failures, so exit code alone is not acceptance.
- [Persistent::execute/import/result](https://github.com/joomengine/Joomla-Component-Builder/blob/037752c7e6599aa4cec900138dfb61af7ee4ba8f/libraries/vendor_jcb/VDM.Joomla/src/Componentbuilder/Import/Item/Persistent.php) sets processing state, resolves the stored file, loops rows and collects errors. Row exceptions can coexist with earlier writes; persisted status/messages are not a batch transaction. An interrupted process can leave a processing job.
- [Persistent Message](https://github.com/joomengine/Joomla-Component-Builder/blob/037752c7e6599aa4cec900138dfb61af7ee4ba8f/libraries/vendor_jcb/VDM.Joomla/src/Componentbuilder/Import/Persistent/Message.php) archives prior messages and persists the current set during `result()`. Verify the entity's configured log table against the generated view/query; similar names do not prove agreement.

Two further limitations were found in the 11 November follow-up:

- The [queue Template](https://github.com/joomengine/packages/blob/4fd6ce1f2a11a478abb291d03a1a3b32ceeda5c9/src/template/dbf2580a-f6a5-4963-8103-85b996a5bed7/item.json) generates a malformed quoted `onclick` for its info action and literal `row.guid`/`row.target` arguments. Clicking the completed job's info icon produced `SyntaxError: Unexpected end of input`. Correct the maintained Template and recompile when adapting this feature; a Completed job does not prove the message UI works.
- [Persistent.Entity](https://github.com/joomengine/super-powers/blob/9cd980492bed4c8177a6e32b703641950ec93604/src/7cc3c19c-155c-4b34-8f9d-5e11705195fe/code.power) defaults its message-log table to `message_log`, while Demo's schema/endpoint uses `importer_message_log`; the inspected ItemImport configuration does not align it. This is a source inconsistency to resolve and test, not evidence that the successful job failed. Inspect real persisted messages and the modal separately before claiming error-log coverage.

For one controlled processor, serialize execution. If multiple workers are required, use a supported atomic claim with ownership/expiry and recovery, and test competing workers. A status update alone is not a lock. Before retrying, use the application's stable match keys or operation identity to avoid duplicate rows, or reconcile the exact partial state first.

## Acceptance and failure recovery

In a disposable target, prove the complete journey: **download example → fill a synthetic row → upload → inspect/correct mapping → save job → execute registered processor → inspect application rows → open queue/status and row messages → verify file retention/cleanup**. Confirm the uploader's progress/error/delete controls and that the example and mapper agree. Test missing file, invalid mapping, one bad row, repeated job, mid-process interruption and two competing processors if concurrency is advertised. Test staff upload/queue visibility separately from the processor's execution identity and domain permissions.

On failure, retain job GUID, input identity, mapping, last known state and sanitized row errors. Inspect completed writes before resetting a job to waiting. Correct the maintained configuration or focused domain Power, compile again and retry under the selected policy. Record the actual processor, scheduling and concurrency checks relevant to the deployment.
