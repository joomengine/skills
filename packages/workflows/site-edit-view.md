# Build native frontend create and edit views

Use this workflow when signed-in site users need to create or update an application record. Start with a writable [Admin View](../models/admin-views.md) and its existing Fields, model and table. Enable its generated frontend form on the [component's Admin Views attachment](../models/component.md#attach-views-through-full-linking-records). A separate [Site View with a Dynamic Get](dynamic-get.md) can list records and link to that form, but it is not the write model. Do not start by hand-writing a form, duplicating a table or patching the generated Joomla files.

Use an authorized disposable [Playground](../../testing/playground/README.md) with the intended JCB, Joomla and PHP versions. Keep a known-good source checkpoint. The fixture below is for learning and validation; it does not change the existing [Note Desk scenario](../../examples/note-desk.md).

## 1. Build a small record and decide access

Create a small component (for example, `Entry Desk`) or use a separate test copy of an existing one. Add a writable Admin View named **Entry** (plural **Entries**) with a database-backed, required short text Field for its title. Reuse the generated record ID, ownership and publishing fields; do not add duplicate columns for them. Attach the view to the component and confirm the installed backend can save and reopen an Entry before diagnosing a frontend form.

Define the roles before wiring links. For the fixture, use two separate ordinary accounts in the same dedicated contributor group, plus an administrator to configure and inspect results. Contributors need access to the intended frontend navigation/form and permission to **Create** and **Edit Own**. Do not grant broad **Edit**, **Edit State**, **Edit Created By**, or administrator access merely to make the form open. For an application that does need any of those permissions, grant it deliberately to the intended role and add a separate test for it.

Configure the applicable actions on the Admin View, then set the effective permissions under the **installed component's Options → Permissions**. Review generated ACL definitions and Joomla inheritance at component and record scope; a setting of Inherited is not a promise that the effective action is Allowed. Sidebar/menu visibility, Joomla viewing access levels, an entity's access action and write permissions are separate decisions. Do not rely on hiding a button to enforce a write rule. See [Joomla ACL permissions](https://manual.joomla.org/docs/next/general-concepts/acl/acl-permissions/).

## 2. Enable the form on the attached Admin View

1. Open **Joomla Components**, edit the component and open its **Admin Views** attachment editor. Find the row for **Entry**, not a Site Views row and not the Field definition.
2. Set **Edit/Create Site View** (`edit_create_site_view`) to **Add** (`1`) to generate the site form without requesting a menu type. Choose **Add+Menu** (`2`) only if you want JCB to emit the corresponding menu entry type as well. The empty **None** choice does not opt in. **Add+Menu** does not create a Joomla Menu Item or grant a visitor access; after installation, create a Joomla Menu Item separately if the application needs one and configure its viewing access.
3. Save, reopen and verify the row still points to the intended Admin View GUID and retains the chosen value. If authoring via a blueprint, edit the same row in the component's `component-admin-views.json` child, then import or refresh it and reopen the GUI.

The labels and positive-value generation condition are verified from the JCB 6.x [attachment form](https://github.com/joomengine/Joomla-Component-Builder/blob/037752c7e6599aa4cec900138dfb61af7ee4ba8f/admin/forms/component_admin_views.xml#L726-L741), [language label](https://github.com/joomengine/Joomla-Component-Builder/blob/037752c7e6599aa4cec900138dfb61af7ee4ba8f/admin/language/en-GB/en-GB.com_componentbuilder.ini#L2318-L2321), [compiler generation](https://github.com/joomengine/Joomla-Component-Builder/blob/037752c7e6599aa4cec900138dfb61af7ee4ba8f/libraries/vendor_jcb/VDM.Joomla/src/Componentbuilder/Compiler/Component/Structuremultiple.php#L394-L407), and [menu XML emission for value 2](https://github.com/joomengine/Joomla-Component-Builder/blob/037752c7e6599aa4cec900138dfb61af7ee4ba8f/libraries/vendor_jcb/VDM.Joomla/src/Componentbuilder/Compiler/Architecture/AdminViews/EditView.php#L663-L678). Use the [current-version policy](../../standards/version-policy.md) and confirm the emitted files on the actual target.

## 3. Route through the generated controller and form

Compile and inspect the installer before wiring links. With Joomla 6 names and the example singular code name `entry`, look for the site equivalents of `src/Controller/EntryController.php`, `src/Model/EntryModel.php`, `src/View/Entry/HtmlView.php`, `forms/entry.xml` and `tmpl/entry/edit.php`. Check the real code names, controller, form target, task prefix and generated token. With **Add+Menu**, inspect the emitted XML and actual menu type in Joomla before relying on it.

Use the installed native form/menu and tasks. For a separate read page, build authorized Create and Edit links to the generated singular controller tasks, using Joomla routing. The route shapes to verify are `index.php?option=com_entrydesk&task=entry.add` and `index.php?option=com_entrydesk&task=entry.edit&id=<numeric-record-id>`. Substitute the generated component/view names and the actual key accepted by the controller. The edit task normally establishes the form's edit context; a direct view URL or a plural list task is not a substitute. Keep definition GUIDs, portable application GUIDs and the controller's accepted Joomla record ID distinct. If an existing controller deliberately resolves a GUID, reuse that verified mechanism instead of inserting a GUID into a numeric `id`.

Keep native save/cancel dispatch, form token and input validation. Check where these actions actually return on the installed target; the controller's list, referral or return behavior may depend on its configuration. Start with that default. If the application needs a different destination, use the supported controller path and accept only a legitimate internal Joomla return target. Do not build a second save endpoint merely to change a redirect. Use [native code placement](../../examples/reference-patterns.md#native-code-placement-and-composition) to locate the appropriate authored field if an extension is necessary.

In the public Joomla 6 examples, [Hello World Greeting](https://github.com/vast-development-method/hello-world-joomla-component/blob/a81c0dd8b8f41905671a86796a3e5995685fdaba/site/tmpl/greeting/edit.php#L92-L98) shows the generated edit layout and token alongside a separate Greetings read view. Use this historical output for structure only. Service Directory's [Company controller](https://github.com/joomengine/Joomla-Service-Directory/blob/d25ca95084d79e552e2ae99f67011679d41d3ad4/site/src/Controller/CompanyController.php#L149-L218) illustrates separate add and edit/owner checks: the owner is read from the stored record. Its [Company model](https://github.com/joomengine/Joomla-Service-Directory/blob/d25ca95084d79e552e2ae99f67011679d41d3ad4/site/src/Model/CompanyModel.php#L408-L427) disables and excludes publishing/ordering fields when the user lacks Edit State. Check both the controller and model on the target. Do not assume that Edit Own requires Edit State or that every older/custom model uses the same ownership check.

## 4. Prove the installed flow

Install the compiled extension in a clean consumer or isolated test copy. Observe the real frontend session for each role; testing as a Super User does not exercise contributor permissions.

| Case | Expected outcome to verify |
| --- | --- |
| Contributor A creates an Entry through the site form | A valid title saves once; the stored owner is A. Required validation rejects an empty title without creating a record. |
| A reopens and edits their own Entry | Edited title persists after reload. No publishing, ordering or ownership change is allowed by the contributor role; check the saved record as administrator, not just what the form shows. |
| A opens the form, types a different title, then cancels | Expected internal page opens and the stored title is unchanged. Check checkout release when the target uses checkout. |
| Contributor B has the same role but does not own A's Entry | The frontend edit flow denies access to A's record and leaves it unchanged. B can still create and edit B's own record. |
| Logged-out visitor | No write access; check the intended login/denial response. A read page can remain public if that is the design. |
| Selected menu/return behavior | **Add** works through the intended native task links. If using **Add+Menu**, verify its real Menu Item separately. Check return paths after save and cancel, including with SEF enabled if used in production. |

If no form is generated, reopen the attachment and verify **Edit/Create Site View** before editing code. For a wrong page or a missing route, confirm the installed version, singular code name, menu item and controller task before changing ACL. For a denied action, check the actual user's effective permissions and stored owner; do not widen group permissions just to get a passing test. If a reversible source change is needed, fix the authoritative JCB records and regenerate.
