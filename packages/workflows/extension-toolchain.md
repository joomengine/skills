# Build and verify Joomla extensions with JCB's native toolchain

Use this workflow when a component needs a module, an event plugin, a different router mode, or installer lifecycle code. Start with the [extension](../models/extensions.md) and [component](../models/component.md) model guides for exact record and field contracts. Use the [version policy](../../standards/version-policy.md) and [Playground](../../testing/playground/README.md) for authorized validation. Record the Joomla/JCB/PHP versions, component and extension GUIDs, intended Joomla client or plugin group, and the expected installed behavior. The exercises below specify acceptance cases, not completed runtime tests.

## Choose the native extension and its installed check

Use a **module** for a positionable UI block, a **plugin** for an event that the owning Joomla application actually dispatches, and the **component** for its own pages, request handling and data. The [manual's module primer](https://github.com/joomengine/jcb-documentation/blob/903321d59da7352cd20dfada1a2787b17ce669db/english/Joomla-Modules.md) and [plugin primer](https://github.com/joomengine/jcb-documentation/blob/903321d59da7352cd20dfada1a2787b17ce669db/english/Joomla-Plugins.md) explain those roles. A [compiler plugin](compiler-plugins.md) is a separate authoring prerequisite, not a site behavior plugin; a runtime [webservices plugin](../models/api-selection.md) supplies an API event contract.

1. **Site module exercise:** Create a Joomla Module with Site target and a concrete Text Field named `badge_label` for a configurable label. Put that Field in the module configuration fieldset, not a standalone form-file group. In the default template, read the saved value from `$params->get('badge_label', '')` in the installed module template context and render it as safe plain text using the [project output policy](../../standards/authored-code.md#use-native-helpers-for-frontend-output). Use the [language-string workflow](language-strings.md) for static interface labels. Start with the generated dispatcher and no helper unless the feature requires data or a service; do not assume a legacy entry script is the active Joomla 6 path. Attach the module in **Component Modules**, compile, and inspect the module ZIP's manifest, configuration field, dispatcher/provider and template. On the consumer, create or configure an instance, assign a position exposed by the active template, publish it on one intended menu item, and set a distinct label. Verify that the label reopens in Module Manager, renders on that page and does not appear on an unassigned page. Test an empty value and special characters against the expected fallback and output policy.
2. **Content plugin exercise:** Create a Joomla Plugin in the `content` group with a compatible CMSPlugin base; use the target's `ContentPrepareEvent` contract for `onContentPrepare`. In **Main Class Code**, add a typed handler that returns without changes unless `$event->getContext() === 'com_content.article'` and the item exposes text. Use `$event->getItem()` and replace only the fixed marker `{jcb-toolchain-probe}` in its text with a harmless value. Keep class-body code separate from the header and resolve class imports through the [Joomla Power policy](../../standards/authored-code.md#let-jcb-resolve-class-references). For a custom-named handler, provide an explicit `public static function getSubscribedEvents(): array` mapping to it; inspect the generated subscription even when the compiler infers events. Attach it in **Component Plugins** and inspect the compiled plugin ZIP's manifest, provider, class, subscription and language/parameter assets where applicable. Install and enable that plugin in a disposable consumer; view one Joomla article with the marker, one without it, and the marker article again with the plugin disabled. Expect replacement only in the intended context while enabled. This verifies the real event behavior without a production side effect.
3. **Verify the artifact set, not just the component ZIP.** Reopen the saved attachment rows and confirm their compile/export choices. Install the actual component/module/plugin ZIPs required by the consumer, then explicitly enable/publish and configure them. JCB's inspected **Install All** action installs separate emitted extensions in a loop; an attachment is not proof of a combined Joomla package ZIP. Test a combined installer only if a real package artifact is part of the requested delivery. Retain the [editable source and required artifacts](../../workflows/delivery.md) with install/enabling order, module position, event trigger, version and observed results.

If output is missing, check attachment and target before investigating PHP. If it is installed but inactive, check the module client, template position, access/menu assignment or plugin enabled state, event group, active application and signature. Inspect dependencies and generated files without making a lasting repair there; correct the owning JCB record, recompile and retest.

## Place a PHP Power inside a module or plugin

Prefer the generated dispatcher/plugin entry point calling a small Power. Use the [PHP customization procedure](../../super-powers/workflows/customize-extension.md) for class body, dependencies, actual caller and compiler settings. At the inspected source baseline, the Power's namespace selects the extension build folder and its dotted final segment selects a subpath under that extension's `src/`. Use the resolved module namespace/client or plugin group/name from the actual consumer manifest/provider. Do not infer those from display names.

- For a site module whose compiled namespace includes `Module\StockBadge\Site`, a Power named `BadgeLabel` with namespace value `[[[NamespacePrefix]]]\Module\StockBadge\Site\Service.BadgeLabel` is intended to build as `src/Service/BadgeLabel.php` **inside the module ZIP**. For an administrator module use its actual `Administrator` namespace. The client controls the installed module context, not a second `site/` directory in its ZIP.
- For a content plugin whose compiled namespace includes `Plugin\Content\StockMarker`, a Power named `MarkerFormatter` with namespace value `[[[NamespacePrefix]]]\Plugin\Content\StockMarker\Service.MarkerFormatter` is intended to build as `src/Service/MarkerFormatter.php` **inside the plugin ZIP**. These are illustrative settings values; escape backslashes when writing JSON. Verify case, path, package inclusion and the installed caller; a source file alone does not prove activation.
- Reusing a generated class's exact namespace and filename is an intentional replacement, not an additive service. The [manual's dispatcher and plugin examples](https://github.com/joomengine/jcb-documentation/blob/903321d59da7352cd20dfada1a2787b17ce669db/english/Power-Based-Class-Overriding-and-Source-Injection.md#L92-L198) illustrate this. Prefer a fresh class path; when replacement is needed, record the replaced class, retained provider/event/API contract, why normal hooks are insufficient and how to remove the replacement. Compare clean output with and without it, and rerun installed behavior after compiler updates.

## Router and installer lifecycle

- **Router:** Follow the [Site Router workflow](site-router.md) to choose Default or Code, check what Manual does in the installed compiler, and validate URLs through the compiled component. Service Directory J6 is the worked example.
- **Lifecycle:** Keep schema/data and versioned update SQL in their native models; use an installer hook only for behavior that SQL, native setup or a runtime event does not express. Choose the supported constructor/preflight/postflight/uninstall slot and its enable field for this extension, not a similarly named slot from another model. Inspect generated script/SQL and run the real fresh install; use a disposable copy for uninstall or upgrade, check both expected data preservation/removal and errors, and do not exercise destructive hooks on the source site. See [retained update SQL](compiler-plugins.md#retain-historical-update-sql) and [target migration](migrate-target.md); a successful first install is not upgrade evidence.

## Optional: use the actual installed JCB CLI

The native Joomla console is an optional alternative for operations the installed JCB Commands plugin exposes. In a compatible authorized Joomla host, confirm the plugin is installed/enabled and run from that site's Joomla root:

```bash
php cli/joomla.php list
php cli/joomla.php componentbuilder:compile:component --help
```

Use the compile help before choosing the component identifiers, target, options and auto-install flags. The [manual CLI suite](https://github.com/joomengine/jcb-documentation/blob/903321d59da7352cd20dfada1a2787b17ce669db/english/CLI-Command-Suite.md#L243-L331) shows the available input forms and options at its documented baseline. For package operations, discover `componentbuilder:<action>:<area>` in the installed command list and use its help; do not substitute a name guessed from another area. Keep [Init/Pull/Reset/Push effects and destination checks](../../standards/repository-operations.md) explicit. Start with a read/inspection operation, compile without automatic installation unless intended, and validate the resulting real artifacts as above.

This console plugin is not an MCP transport, a compiler-event plugin or an application's queue worker. A Playground embedded console or an available GUI route does not prove the host CLI and every option are available. If command help or the required runtime capability is absent, use the supported GUI for the same JCB workflow and report the unrun CLI check.
