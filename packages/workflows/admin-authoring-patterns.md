# Native form conditions, options and administrator actions

Use these worked recipes when an application needs conditional editing, per-menu configuration or an administrator operation. Keep the Fields, associations, code and action definitions in JCB. These are small reusable patterns, not a component-specific replacement framework. Follow [the authoring boundary](../../standards/authored-code.md#keep-implementation-inside-jcb) and the [Admin View model](../models/admin-views.md) for the surrounding contracts.

**Evidence:** inspected 20 November 2026 against JCB `6.x@037752c7e6599aa4cec900138dfb61af7ee4ba8f`. The English manual supplies teaching context; the pinned compiler/form sources below establish implementation details. These recipes are source-reviewed instructions and acceptance cases, **not newly executed Playground/runtime results**. Resolve the current target using the [version policy](../../standards/version-policy.md).

## 1. A controlling List and its dependent field

**Outcome:** an edit form has `delivery_mode` with values `0` (Pickup) and `1` (Delivery). The `delivery_note` text field appears for Delivery. Changing back to Pickup hides it. This example deliberately **retains** the note for later reuse; consumers ignore it when mode is Pickup. A requirement to clear inactive data is a different persistence policy, not something to infer from visibility.

### Author the native records

1. Create/reuse a List Field named `delivery_mode`, using the supported List Field Type. Set a single selection, integer filtering, a default of `0`, and these option values and labels through the Field editor:

   ```xml
   <option value="0">Pickup</option>
   <option value="1">Delivery</option>
   ```

   These are the option entries, not a complete exported Field record. Retain the Field Type's required XML and the application's actual database/storage settings. Option **values**, not translated labels, drive conditions.
2. Create a Text Field named `delivery_note`. For this first slice leave it optional; do not introduce conditional requiredness before visibility and persistence work. Attach both Fields to the same real Admin View using `admin_fields.addfields`. Neither should be marked non-database if the values must be saved. Attach that Admin View to the component.
3. In that Admin View's Fields Conditions, add one condition: target = the `delivery_note` Field; match field = `delivery_mode`; match behaviour = **Is** (`1`); match options = `1`; target behaviour = **Show / Toggle** (`1`); target relation = **Isolate** (`0`). Save and reopen the owning records to verify the actual Field references and values. Do not substitute custom show/hide JavaScript for this native rule.
4. Compile, retain the installer and inspect the emitted edit-form XML, generated condition script and stored-column definitions. The compiler resolves the selected GUIDs against the view's attached Fields. A correctly spelled name without the matching attachment is insufficient.
5. Install and exercise the edit form. The generated script supplies initial evaluation and change listeners; confirm both rather than accepting a successful toggle alone.

### Prove saved, reopened and stale-value behaviour

- On a new record, Pickup hides the note. Switching to Delivery shows it. Save `Leave at reception`, close, and reopen: Delivery and the note must survive, and the note must be visible immediately.
- Switch that record to Pickup, save and reopen. Check the actual stored value, not merely the hidden control. For this recipe the old note remains, but the rendering/business consumer must not use it while mode is Pickup. Switch back to Delivery and verify the retained note reappears.
- Exercise zero, empty and invalid submitted modes deliberately. `0` is a legitimate option here, not an absent value. Enforce the accepted values server-side through the supported Field validation/model contract; hiding controls is not authorization or protection from a crafted request.
- If the real requirement says inactive notes must be erased, implement that specific normalization in the appropriate JCB save hook or a called Power, then test the stored value and reopening again. Do not assume the native visibility condition clears data.
- If Delivery must require a note, set the Field's required contract and test the target compiler's conditional validation: visible+empty fails; hidden+empty behaves as intended; tampered browser `not_required` data cannot waive server requirements. Inspect generated validation before adding a competing handler.

If behavior is stale after changing the definition, first reopen JCB's saved condition/Fields, inspect the new installer, verify the installed extension is that build, and reload its generated assets. Do not “repair” the installed JavaScript and leave the authoring rule unchanged. A dependent **option catalogue** (for example cities filtered by region) is a different problem: use a suitable native/custom Field and its data relationship, not this visibility rule alone.

## 2. Component defaults with menu-specific overrides

**Outcome:** a Site View has a `show_title` Yes/No setting. The component default is Yes; one Joomla menu item inherits it and another explicitly chooses No. This is configuration, not an Admin View database column.

1. Create/reuse the `show_title` Radio or List Field with values `1`/`0` and default `1`. Leave its extra `display` property unset for availability in both configuration and menu contexts.
2. Attach it through the component's **Global Config** (`component_config.addconfig`). Set the row's `tabname` to the target Site View's exact **Name**, not its visible title or an assumed code name. The inspected compiler matches that name to make these configuration Fields available as frontend parameters.
3. Ensure the Site View is attached to the component and has its native menu type enabled. Compile and inspect both the component's options XML and the generated Site View menu metadata. This creates a menu **type**, not an actual configured Joomla Menu Item.
4. Install and set the component's Show Title option to Yes. Create two menu items of that generated type. Leave item A on **Use Global**; choose No for item B. Save, close and reopen both to check persistence.
5. In the Site View's JCB-authored presentation, read the effective parameter available in that generated context and conditionally render the title. The Joomla 6 site-view template initializes `$this->params` from the site application (with a component-params fallback). Do not replace it with a component-only read that ignores menu overrides. Inspect its effective value at both actual menu routes, including their `Itemid`, and confirm empty “Use Global” falls back rather than being treated as No.
6. Change the global setting to No: item A should follow; item B should keep its explicit choice. Then set B to Yes and verify only B changes. Test a route without an active menu and document the intended fallback. Identical view names do not make distinct menu contexts interchangeable.

The `display` variants are native settings, not template patches:

- **Unset:** both contexts. For eligible generated option sets the compiler adds an empty **Use Global** option and relaxes the menu field's default/filter/required settings. Inspect the emitted XML; this is not a promise for every arbitrary Field type.
- **`config`:** component options only; do not expect a menu override control.
- **`menu`:** menu parameters only; specify a useful menu default and do not expect the automatically added global option intended for shared fields.

Use separate Field definitions when two consumers need genuinely different reusable Field contracts; changing one shared Field affects every owner. These `display` rules apply to configuration/menu placement, not ordinary Admin View conditional visibility. If a menu control is missing, check the exact config tab/Site View name match, its display property, component attachment and generated menu metadata before adding PHP or editing installed XML.

## 3. A native administrator action with controller and model

For a toolbar or inline link whose job is to open a different record editor and come back, use [Return to origin](return-to-origin.md). The target’s generated form handles the return; this recipe is for a separate controller operation.

**Outcome:** add a read-only **Check readiness** action to a saved record's edit toolbar. It checks that a project-defined title is present, reports the result and returns to the edit screen. Start with this small observable operation before adapting it into a mutating bulk action. Use a separate synthetic Admin View or an authorized Demo adaptation; do not change a production shared view merely to try the recipe.

1. In the owning **Admin View → Custom Buttons**, enable `add_custom_button`. Add a row with name `Check readiness`, method `checkReadiness`, an appropriate icon, target **Single** (`1`) and type **Default** (`0`). The method value is the method name, not a whole `view.method` route. The compiler constructs the task from the view code and method.
2. Supply a complete public `checkReadiness` method in that view's **PHP Controller** (`php_controller`) area and a narrowly named readiness method in **PHP Model** (`php_model`). These are class-member insertion areas: do not paste an outer class, namespace or `<?php` wrapper into them. Keep the generated class shell and standard CRUD behavior intact.
3. The controller's concrete flow is: verify the Joomla form token; obtain the current user and require the actual generated action permission; read/filter the submitted record identity; reject a new/unsaved or unavailable record; obtain the owning model; call its readiness method; set a translated success/error message; redirect to the owning edit route. Inspect the generated permission key and task instead of guessing from the button's display text. Hiding a toolbar button does not secure a directly requested task.
4. The model loads the authorized persisted record and checks its title. Return a clear result to the controller; do not silently save unsaved form contents as a side effect of a read-only check. For example, an existing record with a nonempty title passes; a missing record or blank title fails. Put a substantial reusable algorithm in a [Super Power](../../super-powers/workflows/customize-extension.md), with a real model caller, rather than copying a service into the installed administrator folder.
5. Save/reopen the JCB view. Compile and inspect the emitted button task, permission declaration, controller method and model method. JCB's Custom Buttons mechanism places authored code and wires the toolbar; a row alone is not an implementation of the requested business action. Resolve JPK/SPK dependencies and use [language strings](language-strings.md) for authored messages.
6. Install and test saved/nonempty, saved/empty, unsaved and nonexistent records. Test an unauthorized direct task and an invalid token; neither must execute protected work. Change the title without saving and click the action: verify the stated persisted-record contract rather than claiming it checked unsaved input. Confirm the return route, message and unchanged database values.

For a **List** action, deliberately use target **List** (`2`), type **Selection** (`1`) when rows are required, and the **list** controller/model areas (`php_controller_list`, `php_model_list`). The generated task uses the list-view code. Filter submitted IDs and authorize each affected record server-side; test zero, one, multiple and partly unauthorized selections. Select **Both** (`3`) only when both contexts have matching implementations. Do not assume the edit controller's method is copied into the list controller, that selection validation grants permission, or that a custom button automatically saves the form first.

If the action is absent, inspect its enable switch, target and effective permissions. If the task is missing, compare the emitted task with the actual public method in the correct generated controller. If the wrong model runs, inspect model selection and singular/list context. Carry corrections back into the JCB-owned slots or Power, then regenerate; no companion system plugin or installed-file patch is required for this native pattern.

Mark source review, compilation, installation and runtime separately. A record saved in JCB, a working toolbar button or a matching XML entry alone does not establish the complete recipe.
