# Upgrade a JCB component without losing data

Use this workflow when a new component release must install over an earlier release and preserve its existing records. A clean install, an in-place upgrade, a same-version reinstall and update-server discovery are separate checks. Keep changes in JCB's maintained definitions; do not patch the compiled ZIP or reinstall from scratch to make an upgrade test pass.

## Prepare a two-version fixture

1. Resolve the current supported JCB release and verify the installed compiler, Joomla, PHP and database versions in the test environment. Use production JCB by default and alpha/beta only for requested development work. See the [version policy](../../standards/version-policy.md) and [Playground integration workflow](../../testing/playground/README.md). Keep the compiler and consumer platform consistent for the comparison.
2. Use a disposable component with an attached [Admin View and concrete Fields](../models/fields-and-relationships.md). For example, create an Upgrade Notes component with a Note Admin View and a persisted `title` Field. Save and compile **A (1.0.0)**. Keep the editable A source and exact installer ZIP; for a real upgrade, start with the actual previously shipped installer, not a reconstruction from the latest source.
3. Install A on a clean test site and create a Note titled `Keep across upgrade`. Record its ID, GUID if present, title and row count. Record the table definition, the installed manifest version and the extension's Joomla schema marker separately: match the component element in `#__extensions` and read `#__schemas.version_id` for its `extension_id`. Record a missing marker as missing. Keep a restorable test-site backup before upgrading, and keep the seeded A site intact.
4. Continue from the same authoring definitions and retained history. Attach a persisted, optional text Field named `summary` to the existing Note Admin View, with nullability/default deliberately chosen so existing rows need no backfill. Preserve the component, view and existing Field identities and generated names. Save and compile **B**, verifying that the resulting component release version advances (for example, 1.0.1). Check the compiler's version/update decisions instead of assuming a version edit alone produces a migration.

## Inspect B before installing

- Check the manifest version and matching `<install>` and `<update>` SQL paths. In the ZIP, confirm the fresh-install table definition contains `summary`. Independently inspect the versioned update SQL and any generated installer postflight: identify what actually adds `summary` on an A site, which update files Joomla can select given the captured schema marker, and whether an operation is missing or duplicated.
- In JCB, reopen the component's [Version Updates records](../reference/component_updates.md). Compare the saved SQL and version rows with the generated files. JCB can discover and persist update SQL using authoring history; a newly imported blueprint does not necessarily have that history. Keep any promised migrations in maintained version-update records or supported native installer hooks, then compile again and confirm the intended migration is still present. Do not derive the expected SQL filename from B's manifest version alone.
- Keep fresh-install [initial data](initial-data.md) separate. Do not replay install seed inserts on upgrade unless the release explicitly needs and tests a data change. Verify any required backfill, rename, removal, or relationship conversion separately; a missing-column check does not establish those behaviors.

## Run and record the acceptance checks

| Test | Expected result |
| --- | --- |
| Install the exact B ZIP over the preserved A site without uninstalling | Joomla reports success; the installed version is B, the schema marker matches the effective update files (or remains absent if no marker is used), and the relevant table has one correctly defined `summary` column. The original Note still has the same ID, GUID if present, and title, with no extra row. Open it, enter a summary and verify it persists. |
| Reinstall that same B ZIP on the upgraded site | No duplicate-column or duplicate-row errors; the original record and its newly saved summary survive. Check the actual schema and record again. |
| Install B on a second clean site | The intended tables and `summary` column exist, create/edit works, and only the expected fresh-install seed data is present. It does not depend on A having run. |

Record the A/B ZIP names and digests, editable source revisions, environment versions, before/after marker, relevant filenames/statements or checker path, schema and row checks, and installer results. For a production release supporting more than one older version, test each supported starting state, including any longer upgrade chain the release promises. Stop on failure, isolate the test copy, restore the preserved baseline for a repeatable retry, and fix the maintained JCB source. For duplicate-column errors, compare the actual starting schema and marker to the selected SQL and postflight behavior before changing anything; do not edit the marker to skip a failed migration.

## Treat release channels as a separate check

The JCB compiler's release channel is not the built extension's update channel. If delivering updates through a Joomla update server, inspect the compiled manifest update-server link and the generated feed. Check the component element, current-to-new version order, supported Joomla target and release stability, and that the download URL resolves to the exact B artifact for that channel. On a disposable A site configured for that channel, refresh Joomla's updates and verify that it offers the correct B; run that update and repeat the record checks. Use an authorized test endpoint if the public feed is not ready. Do not publish or change a production feed as part of a ZIP-only migration test. A manual ZIP pass does not establish channel discovery or download.

## Source evidence and limits

- [JCB compiler: `VersionUpdate::set` and `setUpdateXmlSql`](https://github.com/joomengine/Joomla-Component-Builder/blob/037752c7e6599aa4cec900138dfb61af7ee4ba8f/libraries/vendor_jcb/VDM.Joomla/src/Componentbuilder/Compiler/Extension/VersionUpdate.php#L202-L462) can merge discovered SQL into the previous component version entry, add a separate current entry and generate historical SQL files. Deduplication compares text after removing whitespace, not the installed schema.
- Joomla 6.2.0 [records the initial marker](https://github.com/joomla/joomla-cms/blob/6.2.0/libraries/src/Installer/Installer.php#L1164-L1212) from the latest applicable SQL filename and [skips files at or below the stored marker during upgrade](https://github.com/joomla/joomla-cms/blob/6.2.0/libraries/src/Installer/Installer.php#L1280-L1307). See the [Joomla installation manifest guide](https://manual.joomla.org/docs/next/building-extensions/install-update/installation/manifest/).
- [Service Directory update postflight](https://github.com/joomengine/Joomla-Service-Directory/blob/d25ca95084d79e552e2ae99f67011679d41d3ad4/ServicedirectoryInstallerScript.php#L1669-L1675) invokes a compiled SchemaChecker. Its [Table-backed schema code](https://github.com/joomengine/Joomla-Service-Directory/blob/d25ca95084d79e552e2ae99f67011679d41d3ad4/libraries/vendor_joomservice/JoomService.Joomla/src/Abstraction/Schema.php#L150-L248) can create missing tables and add/check columns. Empty historical SQL files do not rule out that separate mechanism. Verify it exists and runs in the actual target package; this example does not prove a data migration.
- The [English auto-SQL update tutorial](https://github.com/joomengine/jcb-documentation/blob/903321d59da7352cd20dfada1a2787b17ce669db/english/Auto-create-SQL-updates-for-Componets-in-JCB.md) shows the feature's authoring intent. Use it as orientation, not as authority for current version numbering, SQL selection or release configuration.

These are pinned source observations, not required runtime pins or records of a completed fixture. The two-version exercise above is an acceptance procedure, not a reported Playground pass.
