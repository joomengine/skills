## Acquire a feature, preserve its connections

1. Start with the relevant section below. Read the linked `item.json` and its catalogue entry under `index/`; the GUID in its path is the portable definition identity. Custom Code such as `vdmUploaderConfig` uses a natural key instead. Local database row numbers are not portable identities.
2. Use the [repository network](../standards/repository-network.md) to locate the current logical source, then the [package acquisition workflow](../packages/workflows/validate-and-integrate.md#2-configure-acquisition-and-external-sources) to acquire the selected Field, Admin View or component. Acquiring a Field alone does not attach it to a new parent or provide every reverse reference. Inspect parent-owned records such as `src/admin_view/children/<parent-guid>/admin-fields.json` and component view attachments as well.
3. Follow the feature's whole dependency graph: fields and nested fields, persisted Admin Views, Custom Code, Dynamic Gets, templates/layouts, libraries/assets, Field Types, Joomla Powers and Super Powers. Preserve dependency-discovery references in authored code, including intentional layout-reference comments. Configure external catalogues separately. When package records span repositories, follow the acquisition workflow's selected-repository rules; do not assume Pull searches every repository automatically.
4. Apply [entity reuse and identity adaptation](../standards/entity-reuse.md). Unchanged reuse retains its identity; an independent adaptation gets the model-appropriate new identity with coherent remapping. Adapt domain names, target tables, aliases, permissions and data fields together. Keep placeholders and upstream licensing. Importing a whole reference component is useful for exploration; the deliverable should contain the features the requested application needs.
5. Compile and install the consuming extension, then exercise the feature through its real GUI and site output. Use [a comment probe and compiler diagnostics](../packages/workflows/debug.md#trace-a-gui-code-field) to map unfamiliar authoring fields to generated files. Return lasting changes to the blueprint and regenerate.

### Worked trace: Listing from records to rendered page

Follow the table's records as one connected feature, rather than copying the generated model into a new component:

1. **Retrieve:** Listing's `main_get` references Company (`gettype=1`). The Company Dynamic Get selects the Company Admin View, joins category by GUID as one row, and attaches multiple-row collections such as addresses. Its address collection joins address type, country, state and city to return descriptive names. These configured relationships become the query and related-result methods in `ListingModel`, not queries hidden in a template.
2. **Prepare in the model:** Company's `php_after_getitem` defines the mapping from generated properties such as `guidCompanyAddressHH` to presentation properties such as `addresses`, then calls `$this->processItem($this->_item[$pk])`. Listing's `php_model` contains `[CUSTOMCODE=processServiceDirectoryItem]`. That [Custom Code record](https://github.com/joomengine/joomla-packages/blob/a0041f0d408ca65ac43796f89a90c88063fe85a8/src/custom_code/processServiceDirectoryItem/item.json) supplies class members and methods including `processItem()`, `buildItemLink()` and `processLinkedDataSets()`. Preserve its nested Custom Code and Power dependencies. This is maintained native PHP, not an unmanaged model patch.
3. **Hand data to the view:** generated [`Listing/HtmlView::display()`](https://github.com/joomengine/Joomla-Service-Directory/blob/d25ca95084d79e552e2ae99f67011679d41d3ad4/site/src/View/Listing/HtmlView.php) obtains the model's item as `$this->item`, prepares toolbar/document and renders. Keep retrieval and preparation connected to this lifecycle instead of repeating the fetch in markup.
4. **Compose the page:** Listing's `default` invokes `loadTemplate('company')`, `companydetails` and `companyextras`, plus `LayoutHelper::render('companyrelationships', $this->item ?? (object) [])`. The Template entities compile to `site/tmpl/listing/default_<alias>.php`. The `companyextras` Template's Custom View Script takes `$this->item`, then obtains `addresses`, `social_handles` and `portfolios`; its markup passes those collections to Layouts.
5. **Render explicit inputs:** the [Company Relationships Layout](https://github.com/joomengine/joomla-packages/blob/a0041f0d408ca65ac43796f89a90c88063fe85a8/src/layout/ca28683a-d899-4f33-a771-a7b3b95fe2d3/item.json) compiles to [`site/layouts/companyrelationships.php`](https://github.com/joomengine/Joomla-Service-Directory/blob/d25ca95084d79e552e2ae99f67011679d41d3ad4/site/layouts/companyrelationships.php). It receives `$displayData`, prepares category/labels in its Custom View Script, and calls the smaller `companyrelationship` Layout for each group. It does not independently fetch the Company or inherit a Template's local variables.

This is a source-backed composition example, not a blanket endorsement of every business rule or a new runtime/security audit. The blueprint and generated snapshots are separate evidence. For an adaptation, verify the resulting properties, routes, access checks, empty/missing records, nested Layout discovery and asset loading in a fresh compilation and installed consumer. Keep the authoring graph as the source of truth. Shared settings belong in native component configuration, not scattered literals; the generated [Service Directory config](https://github.com/joomengine/Joomla-Service-Directory/blob/d25ca95084d79e552e2ae99f67011679d41d3ad4/admin/config.xml) and [Directory template](https://github.com/joomengine/Joomla-Service-Directory/blob/d25ca95084d79e552e2ae99f67011679d41d3ad4/site/tmpl/directory/default.php) show `max_listings` and `show_login` defined and consumed through parameters.
