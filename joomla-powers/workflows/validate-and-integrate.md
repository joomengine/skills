# Joomla Power integration acceptance

Use the [shared Playground workflow](../../testing/playground/README.md) and [configuration reference](../../testing/playground/configuration.md), or the user's authorized Joomla/JCB environment. Record Joomla, PHP, JCB and candidate catalogue revisions. This procedure is an acceptance specification; its stages are not recorded as passed merely because they are documented.

1. **Static mapping inspection.** Run the offline reference test command in [the examples](../examples/README.md). For candidate mappings, inspect index identity/path/JPK consistency and the selected namespace with `tools/inspect-mapping.sh` from this module. Check source availability and current API methods separately. Include all authorized catalogues and local additions when checking new GUIDs.
2. **Acquisition.** Configure target `2` and the exact read branch. Init the canonical JText mapping `ba6326ef-cb79-4348-80f4-ab086082e3c5` if missing. Reopen it and verify `Joomla\CMS\Language\Text` and fallback row `0`. For a candidate change, use Pull or Reset as appropriate and assert a distinctive saved change so an existing baseline cannot masquerade as the candidate.
3. **Real consumer.** In a disposable blueprint that already compiles, add a maintained PHP method or view code path that calls the JText JPK to translate a component language key. Define that key with a recognizable value. Attach the view/caller to the component and make the path executable; an unused mapping is not a test. A Super Power method may be the caller when testing composition.
4. **Compilation.** Compile the actual consumer for the selected target. Inspect the generated caller: no JPK remains, the expected import exists, and its identifier or alias is used consistently. PHP-lint the resulting file. Do not expect a duplicate Joomla Text implementation in the ZIP. Inspect the generated language entry too.
5. **Installed behavior.** Install in a disposable compatible Joomla site and exercise the caller. Assert the expected translation and correct output escaping. Test the same caller in its actual administrator/site/API execution context, including permission requirements where applicable.
6. **Version and alias cases.** In a task-owned test catalogue, test a fallback row plus an exact row for a genuinely supported target and inspect the selected import. Exercise a consumer already importing another class with the same short name and verify the generated alias and calls agree. Do not modify the public core catalogue for these tests. Reject duplicate version rows under the authoring policy; test missing-target failure using a disposable mapping with neither an exact row nor fallback.
7. **Read-back.** If source export is part of the task, Push the mapping to the authorized destination and branch, inspect every result, then import into a fresh JCB instance and repeat consumer compilation. If only a compiled package was requested, record its artifact/hash and keep the source provenance available.

For every stage record passed, failed, blocked or not run, expected/actual result and source revision. Restore the baseline after destructive fixture tests. Resolve failures in the mapping, caller, dependency configuration or compiler as established by evidence; reimport/recompile/reinstall instead of leaving a generated-file-only patch.
